# 09 验收进 CI：分期方案

> 起因见 `07-verification.md`。07 第一次真跑掉出一个**只在 RHEL 系上出现**的缺陷
> （journalctl 的 `insufficient permissions` 被归成 `internal`，普通用户打开日志页
> 得到 500），它躲过了 400 多个单测与全部本机验证——Ubuntu 上那个请求永远返回 200。
>
> 结论不是「07 该多跑几遍」，而是**能自动化的那部分不该靠人记得去跑**。
> 本文把「验收进 CI」拆成分期，每期有明确的判定标准与退出条件。

## 1. 分期总览

| 期 | 内容 | 触发 | 状态 |
|---|---|---|---|
| P1 | ubuntu + rocky 两发行版跑 root-checks / agent-checks | 每次 PR | **已实现**（`ci.yml` 的 `verify` job） |
| P2 | 慢档：`LONG=1` 的空闲超时；扩发行版矩阵 | 定时（每日/每周） | 未做 |
| P3 | 长时运行：保留期清理、`m_1d` 生成、RSS 曲线 | 常驻实例 + 定期抓取 | 未做 |
| P4 | 浏览器：面板渲染、WS 握手、深浅色 | 每次 PR（前端定框架后） | 阻塞于前端选型 |
| P5 | release 性能计时 | 固定硬件，手工或定时 | 不进通用 CI（见 §5） |

## 2. P1（已实现）

`verify` job：`needs: [package]`，下载 `strixmaid-dist-x86_64`，对
`matrix.distro ∈ {ubuntu, rocky}` 各跑一遍 `scripts/verify/run-in-docker.sh`。

几条已经踩过的决定，别回退：

- **不在 runner 上重新编译**。吃 `package` 出的发布物，测的就是将来要发出去的那份
  二进制。在 CI 里另编一份「差不多的」，测过了也不代表发出去的那份没问题。
- **`fail-fast: false`**。一个发行版挂了要能看到另一个的结果，否则分不清是普遍问题
  还是发行版相关——而「是不是发行版相关」正是这个矩阵存在的唯一理由。
- **两个发行版都要**。只留一个就退化成了本机验证，那个 500 就是这么漏掉的。

## 3. P2 慢档（定时跑，不进 PR）

两类东西不适合塞进每次 PR：

- **`LONG=1` 的空闲超时**：07 §1.2 #15（`elevated_idle_timeout_secs`，默认 300 s）
  与 #16（`idle_timeout_secs`，默认 900 s）。真等要 20 分钟，PR 上不值当。
  另一条路是把配置调小后观察——**但那样测的就不是默认配置的行为了**，
  作为定时任务如实等满更有价值。
- **扩发行版**：Debian 12（与 Ubuntu 同系但 PAM 栈更保守）、Alpine（06 §5.3 只要求
  跑 agent，musl 静态二进制本来就该在上面跑得动）。

判定标准：与 P1 相同的脚本、相同的通过线；只是触发方式和耗时不同。

## 4. P3 长时运行

07 §3 的四项（7 天保留期清理、`m_1d` 层生成、数据库体积曲线、RSS 稳定性）
**本质上不是 CI 能做的事**——它们要的是时间，不是算力。

方案：起一台常驻实例（容器或 VM 都行），定时任务每天抓一次
`GET /metrics/query` 的层级分布、DB 文件大小、进程 RSS，写进一个 CSV。
七天后看曲线，而不是看某一次的快照。**这件事的产出是一条曲线，不是一个绿勾。**

## 5. P4 / P5：明确不进通用 CI 的两项

- **浏览器（§2）**：需要无头浏览器驱动真实渲染。现在只有 `/debug` 单文件调试页，
  正式前端框架未定（`HANDOFF-2026-08-28.md` §2.2：这是架构决定，不该由实施者顺手定）。
  框架定了再设计这一期，否则写出来的东西大概率要推倒。
- **release 性能（§4）**：GitHub runner 的性能在不同批次之间波动很大，
  同一份代码前后两次跑出来的数字没有可比性。**在这种机器上定性能基线只会制造噪声告警**。
  应当在固定硬件上跑，手工或定时皆可，结果记进 07 的表。

## 6. 已知代价与风险

- **CI 分钟数**：P1 每次 PR 增加约 10–15 分钟 runner 时间（两个发行版并行，
  其中 agent-checks 有 150 s 的采集等待是硬等）。私有仓库按分钟计费，值得留意。
- **runner 上的 privileged 容器**：systemd-in-docker 需要 `--privileged` 与
  cgroup v2。GitHub 的 ubuntu-24.04 runner 满足，但这是**运行时依赖不是编译期依赖**——
  runner 镜像换代时可能失效，届时症状是 `systemctl is-system-running` 一直不 ready。
- **150 s 的硬等**：agent-checks 要等 Agent 采集、落盘、推送。这个数字来自采集周期，
  缩短它就等于改被测行为。宁可慢，不要为了 CI 好看去改产品行为。

## 7. 与 07 的关系

07 仍是**清单与预期结果**的真相来源，本文只管「哪些项、什么时候、由谁来跑」。
自动化覆盖到的项在 07 的「结果」列注明「CI」；搬不进来的仍标「人工」，
不因为进了 CI 就假装全覆盖。
