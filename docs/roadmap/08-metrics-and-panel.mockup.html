指标砍掉一半，面板才开始有主次

资源

左栏每条走势下面那道 3 像素的细条，是任务管理器没有的一行。 它画的是这个资源的 PSI 停滞比例——psi.cpu.some / psi.memory.some / psi.io.some。 CPU 20% 但 io.some 60% 的机器，体感是卡死的，而所有传统面板都会显示「一切正常」。 这道细条让「资源没满但任务在等」这件事，在你还没点进任何一页的时候就已经是红的。 组头上的那道，取的是组内成员的最大值——一块盘卡住，整组就是红的。

资源组：一台 24 盘的机器不能铺 24 行

同类资源收进组。组头是入口也是摘要，展开才出成员。这一层不需要任何新指标。

聚合语义

速率求和，饱和度取最大

组头那行数字必须分开算：disk.read_bytes、net.rx_bytes 这类速率求和才有意义；disk.util、gpu.usage、PSI 这类饱和度求和毫无意义，要取最忙的那个。所以组头显示的是「合计吞吐 · 最忙成员 87%」两段，而不是一个平均数——平均数会把一块打满的盘藏进七块闲盘里。

成员格

有身份的印名字，没身份的不印

成员格里放什么，和「有没有详情页」是同一个判据——成员有没有身份。nvme0n1 有型号、有 SMART、有挂载点，名字必须印在格子上，格子还带类型标记（NVMe / HDD），因为异构机器里 HDD 的 87% 和 NVMe 的 87% 差一个量级。cpu137 只有一个编号，没有任何可写的详情，名字不必印，多了直接转热力图。同一个属性同时决定了层数和成员视图的形态。

分组依据

是元数据问题，不是指标问题

多路 CPU 的逻辑处理器网格按 socket 分块，依据是 /sys/devices/system/cpu/cpuN/topology/physical_package_id；网卡分组看 /sys/class/net/*/device；分区归盘看 /sys/block。全都是 /api/v1/system/info 里的静态拓扑，不进时序库，不增加一条 series。

高核数

超过 32 核换热力图

每核一张小图，在 32 核以内还读得动；再多就既画不下、也没人逐核看历史。超过阈值换成单张 canvas 的热力图——一格一个逻辑处理器，颜色深浅是当前占用，仍按 socket 分块。渲染实例数与核数无关，256 核和 16 核的成本一样。而且这时要回答的问题本来就变了：不是「这个核过去怎样」，是「现在哪个核烫」。

页面骨架

组页和详情页是同一个骨架

组页从上到下：聚合图 → 成员区 → 数字与静态事实。成员区在组页里的位置，正对应磁盘详情页里挂载点表的位置——都是「这一页下面挂着什么」。成员区高度封顶、内部自己滚，所以哪怕六十块盘，底下那块文本也不会被顶到看不见的地方。组默认折叠，二十块盘在左栏也只占一行；只有一个成员就不是组，单网卡的机器不该看到「网络　1 个　+」这种废话。

存储并进磁盘了

上一稿单独开了「存储」页，那是错的。

挂载点属于它所在的那块盘，就该列在那块盘的页里。 这样一并解决了上一稿要专门写一段话解释的问题：/ 和 /var 的读写速率为什么一模一样—— 因为它们就列在 nvme0n1 这一页上，共享设备级计数器这件事不言自明，不需要再解释。

读写速率本身不是新指标：/proc/self/mountinfo 第三列是挂载点后端设备的 major:minor， 拿它索引 /proc/diskstats 就能把已有的 disk.read_bytes / write_bytes 归到挂载点上。是一次 join。

跨设备的全局视图放在磁盘组概览页——所有盘一张表，所有挂载点一张表， 「哪个文件系统要满了」一眼看完，不用逐块盘点进去。没有块设备的挂载点（tmpfs、nfs、overlay）也归在那里， 它们没有 disk.* 可 join，速率列显示 —，这是事实不是缺陷。

凭什么砍得掉

不是挑冷门的删，是三条能复述的规则。每一条删掉的指标都能指回它归属的规则。

规则一

派生量不存

fs.usage 就是 used / total，mem.swap_free 就是 swap_total − swap_used，cpu.idle 就是 100 减掉其余。存一条能算出来的曲线，等于白扔一整条 series 的五层桶。前端做一次除法的成本是零。

规则二

同向计数器合成一条异常信号

net.{rx,tx}_{errors,drops} 四条，平时全是零，出事时一起涨。它们要回答的是同一个问题：这张网卡在丢包吗。合成一条 net.errors，非零即异常，面板打红角标；真要分方向，ip -s link 一条命令的事。

规则三

慢变量不进时序库

inode 用量一天动不了一个百分点。它是健康检查项，不是曲线——五层桶存一年，存的是一条几乎水平的直线。挪进 GET /api/v1/system/health 做阈值判断，超了报警，不占 series。

CPU 总9 → 5
cpu.usage保留主曲线，面板上唯一的实线。

侧栏的顺序不是随手排的

GPU 加进来之后侧栏变成五类，配色被逼出了一个硬约束。

绿（GPU）和琥珀（磁盘）是红绿色盲下的经典撞色对，两者相邻时 deutan ΔE 只有 3.7，远低于 8 的下限。 穷举验证过：在固定亮度环上遍历全部五色组合，要让五个颜色在 protan / deutan / tritan 三种色觉下两两都安全， 最好情况的最差 ΔE 也只有 4.9——五个类别色两两全安全，是不存在的。

所以解法不是换色，是排序：把 GPU 挪到 CPU 后面（算力放一起，也更合逻辑），让它只与青、紫相邻，避开琥珀。 按 CPU · GPU · 内存 · 磁盘 · 网络 这个相邻序，暗色与亮色两套配色的五项检查全部通过。 每一行还都带文字标签，颜色从来不是唯一的身份编码。

中性色也全部偏青，不用纯灰；图表底板与进度槽按所属资源的色相染 5–7%， 所以每一页的底色都轻微不同——不是装饰，是让你切页时立刻知道自己在哪一类资源里。

需要你拍板

  1. NVIDIA 怎么接？这条撞上了「静态单二进制优先」。 amdgpu 走 sysfs 是白捡的，主进程直读、零依赖。但 NVIDIA 的利用率只有 NVML（libnvidia-ml.so）给得出来， 而静态链接 musl 的二进制根本不能 dlopen。三条路： (a) NVIDIA 探测与采集下放到 strixmaid-helper——它本来就是动态 glibc，符合原则四，但要给 IPC 加一组指标帧； (b) 每 2 秒 fork 一次 nvidia-smi --query-gpu——零链接，但常驻拉起子进程的开销和味道都不好； (c) P0 只支持 sysfs 能读到的（amdgpu / Intel），NVIDIA 直接标 unavailable。我倾向 (a)，但它是这一稿里唯一会动进程拓扑的改动。
  2. load.5m / load.15m 真的删？这是全表最有争议的一条。论证是「有历史曲线就不需要内核平滑」，成立；但 load: 0.8 1.4 2.1 三元组是运维的肌肉记忆，删了会被骂。折中方案是保留采集但只在 CPU 页角落显示一行文字、不进面板——那就还是 5 条。
  3. disk.iops 合并会不会太狠？读写分离的 IOPS 在诊断「写放大」时有用（写 IOPS 与写 bytes/秒 的比值）。合并后这个判断做不了。代价是每盘多一条。
  4. cpu.freq 加不加？加了任务管理器味道对，不加少一条依赖 /sys 且在虚拟机上大概率探测不到的指标。
  5. 老库怎么办？建议启动时按名单硬删。留着的坏处是 /api/v1/metrics/series 会一直吐出永不更新的死 series，前端还得过滤。
