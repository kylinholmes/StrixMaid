## 3. 这一轮真正学到的东西

三条，每条都是「信号说成功、实际没成功」的同一类错误。记在这里是因为它们会再犯。

### 3.1 终端的退出信号是坏的（**必须先修**）

向一个新建终端发 `exit 42\r`，PTY 回显了 `exit 42\r\n`——命令确实到达了 shell、
shell 也确实退出了。此后 **15 秒内**：零个文本帧（没有 `{"t":"exit","code":42}`）、
WS 不关闭、`GET /terminals` 仍把它列为存活且已附着。再过几十秒才被回收，时机不确定。
显式 `DELETE` 是好的（204）。

两条后果：**客户端永远拿不到退出码**；**已退出的终端继续占着每会话 8 个的名额**。

**为什么活到今天**：`terminal/mod.rs` 那 15 个测试用的是**进程内假 worker**，
真 ConPTY 只有 `worker/terminal/windows.rs` 底层几个测试碰过——
**中间一整段（主进程 registry ⇄ 命名管道 ⇄ worker 双泵 ⇄ ConPTY）没有任何东西端到端跑过。**

**修它的时候**：回归测试必须用真 PTY，不能再用假 worker，否则修完还是不知道有没有修好。

一处线索：`shutdown()` 里 `term.close` 成功走 `info` 日志、失败走 **`debug`**。
默认 `info` 级别下，失败那条**看不见**——排查时先把日志开到 debug。

### 3.2 PowerShell 的 `Set-Location` 不改进程 CWD

实测：`$PWD.Path` 已经是 `C:\Windows`，而 `/api/v1/processes/{pid}` 读到的 cwd 仍是
`C:\Users\kylin\`。cmd.exe 则跟得上。

这一条直接决定了 `12-workspace.md` 的 cwd 联动方案：**轮询进程 cwd 只能当兜底**，
主路径改用 OSC 7（shell 自己报，纯前端解析，后端一行不改）。

**别掉进去的坑**：轮询在 PowerShell 下不报错，它**静默给出旧目录**。文件区会显示一个
看起来很正常的错目录。

### 3.3 HTTP 200 不等于拿到了想要的东西

选图标时从 CDN 抓 Papirus，47 个里 **30 个是符号链接**——CDN 对软链返回的是
**目标路径这个字符串**（15–25 字节），不是 SVG。只检查了状态码，于是把一堆路径字符串
当图标内联进了对照页，统计出的「体积」量的也是那些字符串，**结论因此是错的**
（报的 31,677 字节，真实是 89,824）。

修法是逐个解链 + **断言内容以 `<svg` 或 `<?xml` 开头**。落地取图标的脚本要带这道校验。

这和 §3.1 是同一类错误：**只看信号、不看内容**。

## 5. `11-multi-host.md`：只验了地基

PR #8 只做一件事：证明**完整的 node Router 能跑在一条任意的流上**
（`serve_connection(router, io, peer)`，测试用 `tokio::io::duplex`）。

这是整套设计的支点——约束 4 说「A 只搬字节、不写转发代码」，这句话不成立的话，
yamux 管道、`/nodes/<id>`、SSH 推装全要推翻。**现在它成立了。**

**下一步（yamux）没做，而且我建议动工前先对一下方案**：它要改**正在工作的** Agent
传输层（`ws_agent.rs` 616 行 + `agent/client.rs` 387 行），现有那条端到端用例
`端到端_鉴权_补发起点_行写入_快照` 是直接讲 WS JSON 帧的，换传输就得重写。
行为断言必须一条不少地搬过去——**重写一个还在保护着功能的测试，是安全网最容易悄悄
丢掉的地方**。

风险集中在一处：**WS 消息流 ↔ 字节流的适配器**。axum 的 WS 给的是有边界的
`Message::Binary`，yamux 要的是无边界字节流，适配器要自己管半读与背压。
**这两类 bug 不会在小测试里露头**，要在「大响应 + 慢消费者」的组合下才出现——
而那正是终端刷屏的形状。

项目负责人 2026-09-18 明确表示**多主机不是当前优先级**，所以这条线暂停。

## 7. 明确搁置的事

按项目负责人 2026-09-18 的决定：

1. **Windows / macOS 的端到端验收不做。** 现状：Linux 有 `verify` job，在 ubuntu +

   这被判为 corner case，先放。记在这里是因为 `11-multi-host.md` §3.5 的推装方案原文是
   「复用 `packaging/` 下三套现成的安装脚本」——三套里有两套没被验证过。
2. **94 处 rustdoc warning 不修。** 其中约一半是 `cfg` 门造成的（`unix`/`linux`/`macos`
   模块在 Windows 上本就不存在），只能去掉链接标记，修不"好"；另一半是真打错的路径。
   `cargo doc` 也没进 CI。
3. **`.gitattributes` 一直没定。** `core.autocrlf=true` 且仓库没有 `.gitattributes`，
   工作区是 CRLF。至今没出过事，但提过两次都没答复。

## 8. 会咬人的地方

- **本机开发要登录，得自己指 `helper_path`。** 默认值是裸名字 `strixmaid-helper`，
  靠 PATH 查找，而 target 目录不在 PATH 上——症状是登录页说「认证组件不可用」。
  写一份带绝对路径的开发配置即可，不必改 PATH。
- **Windows `service install` 需要管理员权限，本轮从未真正验证过。**
  单测只覆盖了「写进注册表的命令行长什么样」。
- **`capabilities.system` 的字段名是 Linux 词汇**（`systemd` / `journal` / `polkit` /
  `user_units` / `podman`），在 Windows 上被借去表示「服务提供者可用」「日志提供者可用」。
  功能上没错，语义上是撒谎的。新增能力标志时这个问题会被放大，值得一并想。
- **`docs/roadmap/` 下的 01/02/04/05 已删除**，但代码注释里仍有约一百处引用它们。
  那是**刻意保留的**——它们标注的是某段代码当初为什么这么写。要查走 git 历史，
  `docs/roadmap/README.md` 里写了这件事。
