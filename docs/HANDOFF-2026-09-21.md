## 2. 本轮落地的东西（细节看代码，这里只记决定）

| PR / 提交 | 内容 | 推翻了什么 |
|---|---|---|
| [#15](https://github.com/kylinholmes/StrixMaid/pull/15) | 层叠导航、系统图标、服务端缩略图 | §4.7「worker 不进图片解码库」 |
| `8147e66` | macOS HEIC 缩略图 | 上一条自己刚记下的「HEIC 没有缩略图」 |

三条**推翻既有决定**的记录，理由都写在对应模块的文档注释里，这里只留索引：

1. **§8 未决 8「取系统真图标」从「倾向不做」改为做了。** Windows 走
   `SHGetFileInfoW`、macOS 新建了 `platform/appkit.rs` 这座 objc 桥。
   判据见 `providers/fs/icon.rs` 模块文档。
2. **§4.7「后端只送字节、浏览器自己缩」改为服务端缩好再下发。** 触发点是实测：
   `~/Pictures/Export` 里相机直出的 JPG 每张 13～27 MiB，而旧设计的 8 MiB 闸
   让**真实照片目录一张缩略图都没有**。风险按三层压，见 `providers/fs/thumb.rs`。
3. **「HEIC 不支持」改为 macOS 支持。** 实测 Apple 的 HEIC 内部只有 `hvc1` 瓦片 +
   `grid`，没有任何 JPEG 编码的项——JPEG 那条「捡 EXIF 内嵌预览、零解码」的
   便宜路在 HEIC 上不存在。借系统解码器（ImageIO）而不是引 libheif，理由见
   `providers/fs/thumb.rs` 的 `system_decodable`。

**体积门槛 15 → 18 MiB**（`roadmap/06 §5.2` 有完整记录）。缩略图解码器让 musl
静态二进制到了 15.96 MiB。先试过砍格式：去掉 gif+bmp 只省 66 KB，不够且丢功能。

## 3. 这一轮会再犯的错（三条）

### 3.1 只量了 macOS 的体积就下「门槛内」的结论

本机 release 10.4 MiB，我据此说「门槛内」，CI 上 musl 静态那份是 15.96 MiB，
当场红。**静态链接与动态链接的体积不在一个量级**，本机数字不能替 CI 下结论。

### 3.2 Windows 专属代码只有 CI 能验

`SHGetFileInfoW` 那段在本机连编译都做不到（项目负责人明确要求不做交叉编译，
交 CI 三平台矩阵）。本轮 CI 抓到一个 `collapsible_if`——clippy 在 CI 上是
`-D warnings`。写 Windows 代码时默认**它一定会在 CI 上红一次**，别指望本机清白。

### 3.3 「fake-worker 盲区」又补了一课

`fs.raw` 的分块此前只有 `raw_blocking` 单测与前端 mock 盖着，**没有任何东西
走过真帧通道**——与 2026-09-18 那次终端退出信号是同一类错误。本轮补了
`fs_raw_大文件经真通道分块取回且字节一致`（`worker/providers.rs`）。
**凡是涉及帧上限、分块、附件的东西，测试必须走 `IpcChannel::pair()` 的真通道。**

## 4. 后续八个模块（项目负责人 2026-09-21 定）

按负责人给出的顺序：

1. **文件写操作 + 预览**（设计进行中，见 §5）
2. **VM 管理**（含控制台）
3. **容器管理**
4. **账户管理**
5. **网络**
6. **存储只读**（分区、挂载点）
7. **定时任务编辑**
8. **一键诊断**

明确**不在**这一轮范围：多主机（`11-multi-host.md`）、软件更新、Prometheus 导出。

### 4.1 排序上的硬依赖（不随偏好变）

- **#8 必须最后。** 它是个收集器，把其余模块的数据打包。早做就得随每个新模块
  回头改一遍。
- **#7 比它的位次便宜得多。** worker 里 `service.timers` 已经在了，服务页也在列
  timer，它是对现有 provider 的扩写而不是新模块。想插一个「小胜」时选它。
- **#2 与 #3 在前端是同一种东西**（列表 → 详情 → 一个全屏交互画面），终端那套
  WS 二进制通道可复用。谁先做谁定形状，第二个会便宜很多。
- **#1 会定下「写操作的统一形态」**（确认对话、审计落库、提权时机、失败回滚），
  #3/#4/#5/#7 都会照着抄。所以它排第一不只是它自己的事。

### 4.2 一条容易被忽略的判据：跨平台稀释

**StrixMaid 相对 Cockpit 的真正差异化是「三平台一致」**（Cockpit 只有 Linux）。
每加一个只在 Linux 上成立的模块，界面上就多一块「在 Windows 上打开是空的」，
这个卖点就被稀释一次。

按这条，#2 VM（libvirt，Linux 专属）、#5 网络（netlink，Linux 先行）是**扣分项**，
#1 文件、#3 容器（podman/docker 三平台都有）、#4 账户是**加分项**。
这不是否决理由，是排序时该放上秤的一个砝码——记在这里是因为它在讨论中很容易被
「哪个功能更酷」盖过去。

### 4.3 多主机被拿掉的连带影响（是好消息）

没有多主机意味着 **#2 的 VM 控制台只需要连本机 libvirt 报告的地址**，不必设计
「连任意节点的任意端口」——那条恰恰最危险（会变成 SSRF 跳板）。少了它，#2 的
安全面小一大圈。

但反过来要记住：**`11-multi-host.md` 仍然只完成了第一步**（`stream.rs` 证明了
Router 能跑在一条流上），yamux 管道、`/nodes/<id>` 代理路由、SSH 推装全未开工。
哪天要捡起它，注意它与 #2 的控制台代理会争夺同一层抽象——两者都是「把一条
字节流从别处搬到浏览器」。

## 5. #1 文件模块：已定的四条 + 未获批的方案

**设计流程停在哪**：走的是 `superpowers:brainstorming` 的架构路径，
已完成「探索上下文 → 澄清提问 → 提出方案对比」，**卡在「方案未获批准」这一步**。
按该流程，下一步是取得批准 → 分段设计（逐段过）→ 写进
`docs/superpowers/specs/` → 负责人审 → 才进 `writing-plans`。
**在批准之前不要写实现代码。**

### 5.1 已定的四条（负责人拍板）

| 决定 | 内容 |
|---|---|
| **终点是 D，先交付 A** | D = 全套含上传；A = 预览 + 下载（不改任何文件）。**A 阶段选的通道形状不能把 D 的上传堵死**，所以设计要按 D 的完整范围写，实现计划再分期。 |
| **预览范围** | 文本 + 图片大图（含 HEIC，服务端已能解）+ PDF/音视频交给浏览器原生标签 + **代码语法高亮** |
| **写操作安全网** | **确认对话 + 直接执行**。不做回收站，不做短时撤销。与「授权外包给操作系统」一致：我们不在用户目录里变出东西来。写操作全进审计（已有机制）。 |
| **B/C/D 的分档** | B = A + 改名/删除/新建目录/移动；C = B + 权限修改 + 在线编辑保存；D = C + 上传 |

### 5.2 核心问题与三个方案（**未获批准**）

核心问题只有一个：**字节怎么在浏览器与 worker 之间走**。三个约束把它逼得很紧：

- worker 的 RPC 单帧上限 1 MiB（`ipc::MAX_FRAME_LEN`）；
- `<a download>` 与 `<video>` **都带不了 Authorization 头**（与图标、缩略图同一个坑）；
- 大文件不是假设：负责人的 `~/Downloads` 里有一个 4 GB 的 `.7z`。

**方案一（我推荐的）：给 worker 开一条专用数据流 + 一次性票据**

- worker 侧新增 `fs.open_stream(path, mode)`，**返回一个附件**——就是
  `term.open` 现在返回 PTY fd/HANDLE 的那套机制。主进程拿着 fd 直接泵字节，
  **不经控制面**。
  - 帧上限消失，4 GB 与 4 KB 同一条路；
  - 控制面不被占住（现在 `/files/raw` 那条路，4 GB 要约 16000 次 hex 分块往返，
    期间同会话的其它调用全排在后面）；
  - 权限模型一行不改：`open()` 仍在 worker 里以登录用户身份发生；
  - **上传天然就位**：同一条流反着泵，不必到 D 档再重构。
- 浏览器侧用**一次性票据**（绑会话 + 绑路径 + 短 TTL）换一个不需要请求头的
  URL，于是能用浏览器原生下载 UI、断点续传，以及**视频拖进度条需要的 Range**。
  同一个机制顺带解决 PDF 与音视频预览——它们都需要「能直接塞进标签的 URL」。

**方案二：全部走现有 hex 分块 RPC，下载用 blob**
A 档一天能做完，但 4 GB 文件浏览器直接 OOM、视频没有 Range 拖不动、
到 D 档必须推翻重做。**与「终点是 D」直接冲突。**

**方案三：主进程直接读写文件**
**已否决**，写在这里是为了说明它被考虑过：主进程可能是 root，它直读文件等于
任何登录用户都能看任何文件，`design.md` 原则 3 的授权模型当场失效。

### 5.3 两个附带的设计点（也未批准）

- **大图预览不送原图**：复用缩略图那套机器开一个「预览档」（长边约 1600）。
  20 MB 的照片送 200 KB 就够看，HEIC 顺带支持。原图只在明确点「下载」时才走。
- **代码高亮的体积代价用懒加载消掉**：动态 `import()`，只在第一次打开代码文件时
  拉高亮器。主包对从不看代码文件的人保持 0.90 MiB 不变。选型倾向 shiki
  （语法精度与 VS Code 同源、按语言按需加载语法包），实测仍臃肿则回落 Prism。
  **注意 `size` 门槛刚被抬过一次（15→18 MiB），不要再随手涨。**

## 6. 12 号方案剩下的缺口

四期都合并了，但有三项**方案自己声明过、却没做**的：

1. **查看文本文件没有界面**（最要紧的一条）。`design.md` 与 12 号 §1 都把范围写成
   「浏览 + **查看文本** + 图标 + 缩略图」，后端 `GET /files/content` 完整可用
   （二进制拒绝、640 KiB 上限、UTF-8 有损转换），**前端零调用**——现在点一个
   `.txt` / `.md` 什么都不会发生。根因是 A–D 四期表里从没给它排期，于是四期做完
   看起来「完成了」。**它已经被纳入 §5 的 A 档。**
2. **未决 3：复用系统图标主题（Linux）** 仍然开着。Windows/macOS 已用系统图标，
   Linux 还是内置图标集。
3. **未决 6：下载** 归写操作那一轮——也就是 §5 的 A 档。

另有一条本轮新增的如实边界：**Linux/Windows 上 HEIC 没有缩略图**。纯 Rust 生态
至今没有 HEVC 解码器（AV1 有 rav1d，HEVC 没有——是专利格局把生态投入改道了，
不是能力问题），而引 libheif 会破坏 musl 静态链接并请进一个新的 C++ 解码器。
